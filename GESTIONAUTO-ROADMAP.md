# Gestion Auto — End-to-End Product and Delivery Roadmap

**Status:** Active program  
**Product target:** A production-ready, French/Arabic rental-agency operations platform for Morocco, based on the BookCars repository  
**Canonical rule:** Update this document whenever scope, evidence, phase status, or acceptance changes. Do not call the product ready while a release gate is open.

## 1. Product intent

Rebuild the observed Gestion Auto experience as an operationally complete product for a rental agency. The target covers the public/customer booking journey and the agency back office: vehicles, clients, contracts, handover/return, planning, money movement, invoices, staff, reporting, documents, notifications, and external services.

BookCars is the implementation base, not the product specification. Retain sound infrastructure and proven workflows; replace marketplace assumptions when they conflict with a single-agency workflow. Do not reproduce private records from the reference account. The reference account is evidence for behavior and structure only.

## 2. Product principles

1. **One source of truth:** every balance, availability state, invoice, and dashboard metric must derive from persisted domain records with documented formulas.
2. **Agency isolation:** every agency-owned record has an explicit agency/tenant scope. Authorization is enforced in the backend for every read and write; hiding a control in the UI is not access control.
3. **Auditable money:** financial records are append-only or have a traceable correction/reversal path. Never silently overwrite a confirmed payment, invoice, cash movement, or approval decision.
4. **Explicit lifecycle:** contracts, vehicle availability, payment confirmation, handovers, returns, and approvals have named states and validated transitions.
5. **Evidence before parity claims:** observed reference behavior, implementation assumptions, and unavailable behavior stay distinguishable. Unknowns remain open until inspected or decided.
6. **Localized by design:** French and Arabic (including RTL) are first-class. Keep source language keys centralized; use MAD as the Morocco default while allowing an agency configuration where the product model supports it.
7. **Integrations are replaceable:** payment, map/GPS, WhatsApp, email/SMS and storage services sit behind adapters and show honest connection/error states.
8. **Useful empty/error states:** every screen handles loading, empty, validation, permission, network, and server failure states.
9. **Protect local data:** preserve existing workspace changes and local development volumes. No destructive cleanup or production-like data migration without an explicit approved plan and backup.
10. **Ship vertical slices:** complete database/API/UI/permissions/localization/verification/docs for a coherent workflow before moving its status to complete.

## 3. What “ready” means

The app is **pilot-ready** only when all P0 gates below are green. General availability has an additional gate after a successful pilot: no unresolved P0/P1 defects from pilot use, approved support/SLA and pricing/legal materials, capacity/security review, tested upgrade/rollback on production-like data, and explicit business-owner go-live approval.

- A real agency can onboard/configure its identity, team, locations, vehicle fleet and clients without editing the database.
- Staff can create, approve, schedule, hand over, extend, return and close a rental contract; availability stays correct under overlapping requests and maintenance blocks.
- Contract pricing, deposits, partial payments, balances, confirmations, reversals, cash/bank movements and invoices reconcile from an auditable ledger.
- The dashboard and reports match documented formulas and agree with source records for a controlled synthetic dataset.
- French and Arabic routes, content, forms, printable documents and RTL layouts are complete for P0 workflows.
- Permissions, tenant isolation, authentication/session controls, input validation, uploads and secrets have been reviewed. No critical/high release-blocking security issue remains unresolved.
- Backups and restore have been rehearsed; migrations have a rollback/recovery plan; production observability and incident instructions exist.
- CI builds the deployable artifacts and runs the agreed automated checks. Browser checks cover the critical end-to-end workflows at desktop and mobile viewports.
- Setup, operator, user, backup/restore and release documentation is accurate. A clean environment can be deployed from the documented process.

Morocco-specific invoicing, VAT/tax, identity-document and contract requirements must be validated with an appropriately qualified local accountant/legal source before the product claims compliance or issues live invoices/contracts. Until that review is complete, keep the rules configurable and the compliance claim open.

GPS, referral/subscription billing, native mobile parity, and nonessential integrations are P1 unless the business explicitly makes them pilot blockers. The release owner records that decision here rather than quietly declaring unfinished work complete.

## 5. Program phases and release gates

Status values: **Not started**, **In progress**, **Blocked**, **Complete**. “Complete” means every acceptance item for the phase has evidence and no known P0 gap remains. Phase status is recorded at the bottom of this roadmap.

### Phase 0 — Product evidence and scope freeze

**Goal:** build a trustworthy product specification before making parity claims.

- Capture reference routes and representative states in REA/browser where access is available: list, detail, create/edit, validation, error, empty, role variants, responsive and RTL.
- Record each observation with route, user role, viewport, timestamp, sanitized evidence pointer, and confidence. Never store passwords, tokens, personal documents, or reference-customer records in source control.
- Label requirements `Observed`, `Inferred`, `Business decision`, or `Unknown`; identify conflicts and ask only when the business decision changes core data, financial/legal behavior, or release scope.
- Inspect BookCars domain model and migration/index behavior before extending an existing entity.
- Create synthetic acceptance fixtures and glossary (agency, client, contract, deposit, receivable, cash session, invoice, return inspection).

**Gate:** route inventory reconciled; all P0 workflows have an evidence-backed flow or explicitly approved product decision; no credentials or personal reference data captured.

### Phase 1 — Domain, tenant and engineering foundation

**Goal:** establish stable agency boundaries and delivery practices before expanding modules.

- Decide and document the single-agency/tenant representation and how existing BookCars suppliers map to an agency. Define future multi-agency boundaries without leaking cross-tenant data.
- Inventory every model, controller, route, background process, frontend and mobile dependency; identify old marketplace assumptions.
- Draft a role matrix in [agency-authorization-matrix.md](docs/agency-authorization-matrix.md) for owner/admin, manager, counter agent, accountant, mechanic/read-only and customer. Resolve its separation-of-duties and identity-privacy decisions before adding staff memberships; enforce each accepted permission server-side.
- Define audit event format, stable IDs, deletion/retention policy, time zone (`Africa/Casablanca`), currency/precision, and migration strategy.
- Normalize API error envelopes, pagination/filter conventions, request validation, logging and trace IDs. Add schema-level/index review and versioned migrations/backups.
- Establish CI for type checks, lint/build, unit/API checks, dependency/security scan and deployment artifact build. Keep secrets out of CI logs.
- Set design tokens, responsive shell, route registry, French/Arabic locale strategy, RTL direction and accessible controls.

**Gate:** role/scope matrix accepted; cross-agency access checks covered at API level; documented migration/backup policy; CI green on a clean checkout.

Staff operational permissions are now enforced server-side in `backend/src/utils/agencyAuthorization.ts`:
- Explicit `AgencyPermission` enum covering bookings, fleet, locations, clients, private documents, expenses and payments.
- Role-to-permission map for Owner, Manager, CounterAgent, Accountant, Mechanic and ReadOnly.
- `hasAgencyPermission`, `agencySupplierId` and `requireAgencyPermission` middleware.
- Staff membership creation/list/update through `backend/src/controllers/agencyMembershipController.ts` with owner-only create/update, owner/manager read, active-membership uniqueness and staff-blocked cross-agency linking.
- Migrated `bookingRoutes`, `carRoutes`, `locationRoutes`, `countryRoutes`, `maintenanceExpenseRoutes`, `rentalPaymentRoutes` and `userRoutes` from supplier-only middleware to capability middleware.
- User controller scope tightened: create/update/get/delete/email-notifications/language/avatar/password/license paths derive agency from `req.agency` or membership and require `ManageClients`/`ReadClients`/`ReadPrivateDocuments`/`ManagePrivateDocuments` where staff operate on agency customer records.
- Supplier contract upload/update/delete and temporary contract cleanup now require `ManagePrivateDocuments` and bind staff to their active agency.
- Private document delivery resolves staff visibility through `req.agency` with `ReadPrivateDocuments`; customer license fields are masked in staff responses unless the role grants private-document read.

Pure policy coverage: `backend/__tests__/authorization.test.ts` passes all 10 synthetic two-agency/role checks: owner has every capability; manager manages bookings/fleet but not memberships; counter agent manages bookings/clients but not fleet; accountant records payments but cannot manage bookings; mechanic manages expenses but cannot record payments; read-only reads permitted data but cannot mutate.

**Security finding in progress:** manual booking create/update previously trusted client-supplied agency and foreign-key values. A supplier could attempt to create or transfer a booking under another agency, link a foreign vehicle, or use locations not offered by its vehicle. Create now derives supplier scope from the authenticated supplier and validates vehicle, customer, locations, dates and status; update preserves stored supplier and validates the selected vehicle/locations/dates before changing linked driver records. The remaining API-wide tenant audit and build verification are still open.

### Phase 2 — Agency, staff, clients and fleet

**Goal:** provide clean master data needed for reliable contracts.

- Agency profile: legal/display name, contact details, address, tax identifiers, invoice settings, currency/time zone and document branding.
- Team: invitations, roles, activation/deactivation, least privilege, password/session reset path, activity history.
- Clients: searchable profile, contact/identity data with field-level access policy, document issue/expiry/verification states, consent/retention, duplicate handling, history and receivable summary.
- Vehicles: plate/VIN/registration, make/model/year, photos, condition, odometer, fuel policy, seats/transmission, pricing, deposit, insurance and required documents/expiries.
- Vehicle availability state is computed from active contracts, downtime and operational state; it cannot be edited into availability when conflicting records exist.
- Import/export includes a preview, field mapping, row-level validation and safe rollback/report; no silent partial import.

**Gate:** owner and counter-agent workflows pass with synthetic data; document access follows roles; import error handling and duplicate behavior are defined.

### Phase 3 — Contract lifecycle, calendar and documents

**Goal:** run a rental from quote/reservation to signed closeout.

- Lifecycle model: draft → awaiting approval/confirmation → reserved → active → return review → completed; cancellation, late, extension, no-show and dispute paths are explicit.
- Contract create/edit validates agency/client/vehicle, pickup/drop-off locations, dates, price breakdown, add-ons, deposit and availability atomically.
- Concurrency-safe vehicle reservation prevents double booking; maintenance downtime participates in the same availability rules.
- Calendar supports fleet search, status legend, month/week/day needs, create-from-slot, conflict explanation and handover/return tasks.
- Handover and return capture timestamp, staff, odometer, fuel, photos/condition checklist, signatures/acknowledgement and damage/fee adjustments with audit history.
- Contract PDF is versioned/snapshotted at issue, localized, printable, and preserves the exact financial terms signed at that time.
- Extensions/amendments recalculate only by explicit, reviewed rules; no silent edits to issued contract terms.

**Gate:** automated and browser scenarios cover reserve conflict, approval, cancellation, late return, extension, handover, return damage and completed contract.

### Phase 4 — Payments, receivables and cash journal

**Goal:** make financial state explainable and reconcilable.

- Define a ledger with immutable posted entries, account, direction, method, source, actor, timestamp, currency and idempotency key. Corrections are reversal/adjustment entries with reason.
- Reconcile historical BookCars booking statuses and payment gateway IDs to opening ledger entries; produce a dry-run report and require an approved cutover before production migration.
- Follow [ADR-001](docs/decisions/ADR-001-booking-money-model.md): `Booking.price` and status flags are not reliable settlement facts. Server-priced checkout snapshot changes are in source but still require a successful build and sandbox verification. Resolve the open business rules before ledger migration or financial reporting.
- Support contract total, deposit, partial payments, remaining balance, due dates, overdue state, payment confirmation and refund/reversal. Race-safe posting prevents overpayment and duplicate webhook/manual posts.
- Define role-based confirmation, cash drawer/bank account, opening/closing balances, transfers, deposits, cash withdrawals, expected vs counted balance, discrepancy reason and approval.
- Cash journal filters by date/account/method/type/source and exports reconciled rows. Every total traces to its ledger entries.
- Payment provider adapters use signed webhooks, idempotency, reconciliation records and explicit pending/succeeded/failed/refunded states. Keep pay-later/manual entries usable without gateways.
- Derive dashboard receivables only from ledger + due policy; specify inclusive period boundaries and Casablanca local-day behavior.

**Gate:** synthetic accounting fixtures balance; reversal and duplicate/out-of-order webhook cases pass; confirmed entries are auditable; no legacy balances disappear.

### Phase 5 — Invoicing, taxes and approvals

**Goal:** issue compliant, traceable agency documents and decisions.

- Invoice numbering is agency-scoped, sequential, concurrency-safe and immutable after issue; void/reissue keeps a linked reason trail.
- Configure VAT/tax rates and rounding rules per agency; retain pre-tax/tax/total line items and currency precision.
- Validate Morocco tax, invoice and contract-document requirements with a qualified local source; record the decision, effective date and responsible approver. Do not present a guessed rule as legal compliance.
- Invoice state transitions, client/contract/payment links, PDF, print, email delivery status and audit events.
- Approval queue filters by age, amount, vehicle and status; captures assigned reviewer, decision, reason and timestamps; only authorized roles decide.
- Exports preserve filters/period/metric definitions and protect identity data by role.

**Gate:** invoice totals match contract ledger fixtures; numbering is unique under concurrent issue; void/approval audit trail verified; printed French/Arabic documents reviewed.

### Phase 6 — Maintenance, expenses and vehicle operations

**Goal:** protect fleet availability and understand lifecycle cost.

- Separate work orders (vehicle downtime/state) from financial expenses. A cost record does not itself imply a service completion or vehicle availability.
- Service schedule, odometer, supplier, category, expected/completed dates, work status, photos/receipts, warranty and reminders.
- Expense entries link to vehicle/work order and optional cash/bank ledger movement. Receipts use private storage, size/type validation, access checks and retention rules.
- Photo-to-expense assistance is optional and always review-before-save; never fabricate an amount from an unreadable receipt.
- Car history combines contracts, inspections, maintenance, expenses and documents.

**Gate:** unavailable vehicle cannot be reserved; work order completion does not mutate historical contracts; receipts cannot be accessed by another agency/customer.

### Phase 7 — Dashboard, reports and exports

**Goal:** provide reliable decisions, not attractive but inconsistent numbers.

- Write a metric dictionary: contracts, fleet utilization, revenue recognized/collected, receivable, deposits, expense, margin, occupancy, overdue, upcoming departures/returns.
- Each metric states source tables, statuses included, date basis, currency/tax treatment, timezone, rounding and known exclusions.
- Date-range reports support agency, vehicle, client, category and staff breakdown; saved filters and CSV/PDF export preserve definition and selected range.
- Performance: paginate lists, aggregate on the server, add appropriate indexes, bound expensive exports and provide progress/cancellation.
- Reconcile dashboards/reports against hand-calculated synthetic fixtures and ledger totals.

**Gate:** every reported amount/count reconciles to source fixture; export matches UI filter and is authorized; large datasets remain responsive.

### Phase 8 — Notifications and external adapters

**Goal:** add reliable communication and integrations without coupling core rental flows to vendors.

- Notification preferences, templates and delivery log for booking/approval, pickup/return, overdue payment, expiring documents and maintenance reminders.
- Email/SMS/WhatsApp adapters report queued/delivered/failed and support retries without duplicate messages. User consent and opt-out rules are respected.
- Maps/GPS: evidence and provider choice first; agency-managed API credentials stored securely; explicit car-device mapping; freshness/accuracy timestamp; stale/offline state; never expose precise location to unauthorized viewers.
- Online payment providers selected by business; store provider tokens only; no raw card data; verify webhooks/signatures; sandbox then live checklist.
- Integration health panel and disconnect/credential-rotation runbook.

**Gate:** provider sandbox path works end-to-end; failure, timeout, retry and duplicate events are handled; integration secrets do not appear in client bundles, UI logs or screenshots.

### Phase 9 — Customer web, mobile and localization parity

**Goal:** make customer-facing journeys coherent with the agency source of truth.

- Rebrand and adapt customer search/quote/booking, identity/document submission, contract access, payment/deposit, modification/cancellation and notification preference flows.
- Mobile uses the same API/domain policies; scope a practical P0 feature set instead of claiming every admin function is mobile-ready.
- French and Arabic translations complete for all P0 user-visible strings, validation, status labels, email templates and PDFs; Arabic RTL tested with real layout direction, not only translated strings.
- Accessibility: keyboard, labels, contrast, focus, screen-reader names and touch target review.
- Responsive review at representative narrow/mobile/tablet/desktop dimensions.

**Gate:** customer and staff journeys pass on supported browsers/devices in French and Arabic; no critical task requires unsupported locale or layout behavior.

### Phase 10 — Security, performance and operational readiness

**Goal:** make the system safe to run and recover.

- Threat model authentication, roles, cross-agency object references, uploads, exports, webhooks, account recovery and PII retention.
- Review dependency vulnerabilities; patch, mitigate or document accepted residual issues with owner and date. Run secret scanning and remove development/default credentials from deploy paths.
- Rate limits, CSRF/CORS/cookie flags, session expiration/revocation, password policy, MFA decision, audit retention and secure headers.
- Validate uploads (content, size, malware scan strategy, private ACL), prevent path traversal and cross-tenant retrieval.
- Load profile primary list, calendar, dashboard and report endpoints; optimize query/pagination/indexes with explain plans.
- Structured logs/metrics/traces, actionable alerts, health/readiness checks, error budget, privacy-safe diagnostics and incident runbooks.
- Encrypted offsite backups, restore rehearsal, RPO/RTO decision, migration backup and rollback rehearsal.

**Gate:** security review has no unresolved critical/high issue; restore meets agreed RPO/RTO; deployment has rollback and incident owners.

### Phase 11 — Pilot, cutover and release

**Goal:** operate with one agency, learn safely, then declare launch readiness.

- Prepare a production-like staging environment with synthetic data and final hostnames/secrets; run the complete regression matrix.
- Define migration and reconciliation for real data; dry run, row counts, financial totals, attachment checks, rollback snapshot and signed acceptance from data owner.
- Pilot with one agency and named staff; support runbook, issue severity, training, feedback, daily reconciliation and go/no-go checklist.
- Release in staged rollout with feature flags, monitoring, rollback, support contact and communication plan.
- Close P0 defects; accept P1 deferrals explicitly with owner/target date; update roadmap and release notes.

**Gate:** business owner approves reconciled data and workflows; engineering/security gates green; support and rollback are ready; pilot sign-off documented.

## 6. Work item and acceptance contract

Every vertical-slice task must include:

1. **Outcome:** user, problem, route/workflow and measurable result.
2. **Evidence:** observed source state or a labeled product decision; known assumptions.
3. **Data/API:** schema, tenant key, validation, authorization, indexes, migrations, idempotency and error behavior.
4. **UX:** desktop/mobile states, French/Arabic strings, RTL, accessibility, empty/loading/error/permission states.
5. **Financial/legal impact:** source of truth, rounding/timezone, audit/reversal, printable artifact and owner approval when applicable.
6. **Verification:** focused build/lint/unit/API/browser checks appropriate to change, fixtures and result. Do not claim unrun checks.
7. **Operations/docs:** setup/config/secrets, monitoring, migration/rollback and user/operator guide changes.
8. **Roadmap update:** mark status, evidence and follow-up gaps in this file and update the route map where behavior changed.

Definition of done for a code slice: implementation merged into the current working tree, authorization and validation reviewed, build and applicable checks pass, actual UI/API state observed, map/plan updated, and remaining limitations named.

## 7. Development-agent system

These profiles are reusable prompt contracts for Codex/Copilot-style agents, not a claim that background agents run continuously. No dispatcher/scheduler is configured by these files alone. The orchestrator selects profiles per task, gives them a bounded scope and the relevant files, and checks their output. Parallelize read-only analysis freely; assign each mutable file set to one implementation owner at a time.

| Agent profile | Owns | Must return |
|---|---|---|
| Product researcher | REA/reference capture, route/workflow mapping, acceptance language | Evidence, confidence, unknowns, proposed acceptance criteria; no code unless explicitly assigned |
| Domain architect | Domain boundaries, lifecycle, ledger, tenancy, API/migration design | Decision record, invariants, data/API plan, migration and security implications |
| Slice implementer | A single assigned vertical slice | Changed files, behavior, checks run, risks, plan updates; no unrelated refactors |
| QA/release verifier | Independent verification against acceptance criteria | Repro steps, exact results, defects, environment/viewport, release blockers; no unrequested production writes |
| Security/privacy reviewer | Authorization, PII, files, secrets, webhook and audit review | Threat findings with severity, exploit path, mitigation and residual risk |
| UX/localization reviewer | Workflow clarity, responsive/accessibility, French/Arabic/RTL | Route/state review, language gaps, viewport evidence and prioritized fixes |

### Agent orchestration loop

1. The `gestionauto-orchestrator` profile owns roadmap continuity; read `AGENTS.md`, this roadmap, `GESTIONAUTO-MAP.md`, repo status and the target module before acting.
2. Select the smallest next **unblocked P0** slice from the current phase; check whether the user has changed priorities.
3. Ask the product researcher/architect to clarify missing behavior in bounded, read-only work. Do not make a financial, legal, privacy or cross-tenant assumption silently.
4. Assign a task ID, phase, one implementation owner, branch/worktree, allowed file scope, edit-vs-review mode and concrete acceptance list. Other agents may review the design or inspect independently; avoid overlapping edits to the same files.
5. Implement one vertical slice; preserve existing local edits, data and setup. Do not reset volumes or copy reference records.
6. Run the required build and focused checks, then independent QA/security review appropriate to risk. Provide sanitized screenshots/logs that do not expose secrets or personal data. Rework until the slice meets acceptance or record a concrete blocker.
7. Update code docs, route map, this roadmap's phase/work log, and user-facing summary. Keep the active goal open until all P0 readiness gates pass.
8. On “continue,” resume from the next P0 item below; do not restart analysis or ask the user to repeat known preferences.

### Priority policy

- **P0:** required for safe core pilot (agency data, fleet, contract lifecycle, ledger, invoices/documents, permissions, French/Arabic, backup/restore, reconciled reporting).
- **P1:** important follow-up (GPS, advanced analytics, referral/subscription, full native mobile parity, optional integrations).
- **P2:** polish/optimization that does not block safe operation.
- User reprioritization overrides this ordering; record the change and its acceptance impact here.
